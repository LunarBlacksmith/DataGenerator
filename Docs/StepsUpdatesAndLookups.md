# DataGenerator steps, update sets and values from tables

A single run can do more than insert rows. It can:

- take a column's values from another table, from rows already in the database or rows generated by the same run (**Value from table**);
- run its row sets in **steps**, one after another, so a later step can use what an earlier step generated;
- **change** rows instead of inserting them (**update sets**), e.g. give some `Pant` rows the `ShirtID` of a shirt generated in step 1.

Everything runs in **one transaction**. If anything fails (a SQL error, too few rows or values, a cancelled run), nothing in the database is changed, and no SQL file is written.

## Value from table

Set a column's **Generation mode** to **Value from table** and enter the source column in the **Settings** cell, or click **▾** to build it from lists:

```
[[database.]schema.]Table.Column [UNIQUE] [FROM ANY | GENERATED | EXISTING] [WHERE filter]
```

| Part                      | Meaning                                                                                                                                                         |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Table.Column`            | The column whose values are used. Any loaded table, including the table being generated. Add the schema, or the database and schema, when the name is not unique. Names with spaces or symbols go in brackets: `[Order Lines].[Line No]`. |
| `UNIQUE`                  | Each value is used at most once, and never a value the target column already contains, so no two rows get the same value. The run fails if there are not enough values. |
| `FROM ANY`                | Values of every row (the default).                                                                                                                              |
| `FROM GENERATED`          | Only values of rows generated earlier in this run: by an earlier step, or by an earlier row set of the same step.                                              |
| `FROM EXISTING`           | Only values of rows that were in the table before the run started.                                                                                              |
| `WHERE pattern`           | Only values that the [pattern](PatternLanguage.md#finding-existing-values-with-a-pattern) could produce, e.g. `WHERE 'S' THEN NUM(digits=5) GREATER THAN 50`.   |
| `WHERE REGEX expression`  | Only values matching a regular expression, e.g. `WHERE REGEX ^S[0-9]{5}$` (not quoted). Needs SQL Server 2025 with database compatibility level 170.            |
| `WHERE SQL condition`     | Only values of rows meeting a SQL condition. `s` stands for the source table (the table the values come from), e.g. `WHERE SQL s.[Size] = 'XL' AND s.[IsActive] = 1`. See [Writing SQL conditions](#writing-sql-conditions). |

Examples:

| Setting                                                       | Values                                                                 |
| ------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `dbo.Shirt.ShirtID`                                           | Any shirt ID, already there or generated now. Values can repeat.       |
| `dbo.Shirt.ShirtID UNIQUE FROM GENERATED`                     | A different shirt generated in this run for every row.                 |
| `Shirt.ShirtCode UNIQUE WHERE S THEN NUM(digits=5) THEN (1 OR 2)` | A different shirt code such as `S048211` for every row.            |
| `Shirt.ShirtID FROM EXISTING WHERE SQL s.[Colour] = 'Red'`    | The ID of a red shirt that was there before the run.                   |
| `Archive.dbo.Shirt.ShirtID`                                   | A shirt ID from the `Archive` database (its metadata must be loaded).  |

Notes:

- The values are converted to the target column's type. Values that cannot be converted, NULLs, and text longer than the target column are skipped.
- Without `UNIQUE`, each row gets a random value from up to 10,000 matching values.
- `FROM GENERATED` needs an insert set of the source table in the same step or an earlier one.
- `FROM GENERATED` and `FROM EXISTING` tell rows apart by the source table's primary key. For a table without a primary key they compare the value itself, so a generated value that an older row also has counts as existing.
- The **Sample values** column shows e.g. *(unique values of dbo.Shirt.ShirtID, chosen while generating)*, as the values are only known then.

## Steps

Every row set has a **Step** (1 to 99, shown next to the row count). The run goes through the steps in order:

1. All row sets of step 1: first the insert sets, then the update sets.
2. All row sets of step 2, and so on.

Within a step, tables are inserted in foreign-key order as before. A later step sees everything earlier steps did, so it can use those rows with **Value from table**, **Generated key** or an update set.
Row set tabs of a later step show a **Step n** badge, and the run order is listed at the top of a generated SQL file.

Drag a Set tab and drop it on the left half of another tab of the same table to **move** it before that tab, or on the
right half to move it after it. The Sets in between shift along while keeping their relative order. A coloured bar
shows where the Set will land.
To **swap** two Sets instead, hold **Shift** while dragging and drop on the other tab (it is outlined); the tabs between
them stay in place. Press **Esc** to cancel a drag.
The selected Set, row counts and column rules are preserved. Moving or swapping changes the order used for sets of the
same step and action, but does not change step numbers or the rule that inserts run before updates.
When there are more tabs than fit, use the **mouse wheel over the tab strip** or its horizontal scrollbar to reach them.
While dragging, hold the tab near either end of the strip to scroll towards that end (further out scrolls faster), or
turn the mouse wheel. Selecting or adding a Set brings its tab into view.

Insert sets run in step 1 unless you change it. **Generated key** columns need an insert set of the referenced table in the same step or an earlier one.

## Update sets

An update set changes rows that are already in a table instead of inserting new ones. Click **Add update set** above the column rules; the new set opens in step 2.

| Setting                      | Meaning                                                                                                                                                          |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Rows to change**           | How many rows are changed.                                                                                                                                       |
| **Rows**                     | **Any rows**, **Rows generated now** (inserted by this run) or **Rows already there** (existing before the run). The last two need a primary key on the table.    |
| **Where**                    | Optional SQL condition the changed rows must meet. `t` stands for the target table (this table, whose rows are changed), e.g. `t.[Size] = 'XL' AND t.[ShirtParentID] IS NULL`. See [Writing SQL conditions](#writing-sql-conditions). |
| **Fail if fewer rows match** | When ticked, the run fails if fewer rows than **Rows to change** match. When cleared, as many matching rows as there are (up to that number) are changed.          |

- Every column starts as **Keep current value**. Give the columns to change another mode; at least one must change.
- The rows to change are picked at random among the matching rows.
- Primary key columns and columns SQL Server generates (identity, computed, `rowversion`) cannot be changed, and **Database generated** is not available.
- Saved settings are not applied automatically to update sets, so they start unchanged.
- Patterns count rows within the update set: `SEQ`, `ROW`, `FIRST` and `LAST` number the changed rows 1, 2, 3, …
- An update set's rows are not counted in the table's row total; the tree shows e.g. `2 sets, 1 update`.

## Writing SQL conditions

The **Where** box of an update set and the `WHERE SQL` filter of **Value from table** take the part of a SQL Server `WHERE` clause that comes after the word `WHERE`.
The table is given a short name (an alias) so its columns can be told apart from those of other tables in the condition:

| Alias | Used in                                  | Stands for                                                                 |
| ----- | ---------------------------------------- | -------------------------------------------------------------------------- |
| `t`   | **Where** box of an update set           | The **target** table: the table of the update set, whose rows are changed. |
| `s`   | `WHERE SQL` filter of **Value from table** | The **source** table: the table the values are taken from.              |

- Write a column as `alias.[ColumnName]`, e.g. `t.[Size]`. The square brackets hold the column name; they are needed for names with spaces, symbols or reserved words, and are harmless otherwise.
- Any SQL Server condition works: `=`, `<>`, `<`, `>`, `LIKE`, `IN (...)`, `IS NULL`, `AND`, `OR`, `NOT`, functions, and sub-queries on other tables.
- Text values go in single quotes: `t.[Colour] = 'Red'`.
- The alias refers only to the current target (`t`) or lookup source (`s`). Another table needs a subquery or `EXISTS`,
  not a second table name substituted for that alias.
- For another table, use the full SQL Server name **`[DatabaseName].[SchemaName].[TableName]`** and qualify its columns
  with a separate alias. For example, `[TestData].[dbo].[Pant] AS p` and `p.[ShirtID]`.
  `[dbo].[ColumnName]` is not a table reference: `dbo` is a schema, not a table or database.
- Brackets are required for identifiers with spaces, reserved words or special characters; ordinary identifiers may
  omit them, but consistently using brackets avoids ambiguity. Database qualification is not inherently required for
  every same-database query, but is safest here because execution may use a different current database.

For an update Set in `Shirt`, this condition finds rows referenced by small pants:

```sql
t.[ShirtID] IN (
    SELECT p.[ShirtID]
    FROM [TestData].[dbo].[Pant] AS p
    WHERE p.[Size] = 'S'
)
```

For a column using **Value from table**, the lookup's `WHERE SQL` condition uses `s`:

```text
TestData.dbo.Shirt.ShirtID WHERE SQL EXISTS (
    SELECT 1
    FROM [TestData].[dbo].[Pant] AS p
    WHERE p.[ShirtID] = s.[ShirtID] AND p.[Size] = 'S'
)
```

Replace `TestData` with the actual database name. These boxes accept a **condition**, not a whole `WHERE` clause.
The update Set's Where box takes only `t.[...] ...`; the lookup expression uses the `WHERE SQL` keyword as shown.

| Condition                                                             | Meaning                                                        |
| --------------------------------------------------------------------- | -------------------------------------------------------------- |
| `t.[Size] = 'XL' AND t.[ShirtParentID] IS NULL`                       | Rows of size XL that have no parent shirt yet.                 |
| `t.[Name] LIKE 'P%' OR t.[Colour] IN ('Red', 'Blue')`                 | Rows whose name starts with P, or that are red or blue.        |
| `t.[ShirtID] IN (SELECT p.[ShirtID] FROM [TestData].[dbo].[Pant] AS p WHERE p.[Size] = 'S')` | Rows whose shirt is used by a small pant. |
| `s.[IsActive] = 1 AND s.[CreatedOn] >= '2024-01-01'`                  | (Lookup filter) only active source rows created since 2024.    |

## Rows already there and rows generated now

To tell the two apart, the run copies the keys of the tables involved (the primary key, or for lookups on a table without one, the source column) into a temporary table straight after the optional cleanup and before step 1.
"Generated now" then means "not in that copy", and "already there" means "in that copy". The temporary tables are removed at the end.

## Generated SQL files

A generated SQL file does the same work when it is run:

- The values of **Value from table** columns are chosen by the script when it runs, so it uses the database it runs in.
- Rows to change are picked when it runs, and the new values are staged in a temporary table first.
- When too few rows or values are found, the script raises an error and rolls everything back.
- The header lists the number of new and changed rows and the run order.

## Errors

Problems are found before anything runs, where possible, and every message says where they happened, e.g. the table, row set and column.

| Message (shortened)                                                           | Fix                                                                                         |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| *The update set does not change any column.*                                  | Give at least one column another mode than **Keep current value**.                         |
| *Update sets cannot change primary key columns…*                              | Leave key and database-generated columns on **Keep current value**.                         |
| *Only tables with a primary key can limit an update set…*                     | Use **Any rows** with a **Where** condition instead.                                         |
| *…no insert set of that table runs in step n or earlier.*                     | Move an insert set of the source table to an earlier step, or use `FROM ANY`.                |
| *The update set must change n row(s), but only m row(s) of the table meet…*   | Lower **Rows to change**, loosen the **Where** condition, or clear **Fail if fewer rows match**. |
| *'Value from table' needs n different values of … but fewer were found.*      | Generate fewer rows, remove `UNIQUE`, loosen the filter, or generate more source rows.       |
| *The WHERE pattern cannot be used…*                                           | Use only the pattern parts listed in [the pattern docs](PatternLanguage.md#finding-existing-values-with-a-pattern), or a `REGEX`/`SQL` filter. |

## Walk-through: shirts and pants

"Generate 50 shirts and 200 pants, then give 20 of the new pants each a different shirt generated now as `ShirtParentID`,
using only shirts whose `ShirtID` is `S` + a 5-digit number above 50 + `1` or `2`." (Here `ShirtID` is a `varchar` key.)

1. Tick **Shirt** and **Pant** in the tree and set their row counts. Their row sets run in step 1.
2. In **Shirt**, set `ShirtID` to the pattern `S THEN (NUM(digits=5) GREATER THAN 50) THEN (1 OR 2)`.
3. Select **Pant** and click **Add update set**. It opens as **Update 1** in step 2.
4. Set **Rows to change** to `20`, **Rows** to **Rows generated now**, and tick **Fail if fewer rows match**.
5. Set `ShirtParentID` to **Value from table** with
   `dbo.Shirt.ShirtID UNIQUE FROM GENERATED WHERE S THEN (NUM(digits=5) GREATER THAN 50) THEN (1 OR 2)`.
   The other columns keep their current values.
6. Generate. Step 1 inserts the shirts and pants, step 2 changes 20 of the new pants. If fewer than 20 different shirts match, nothing is saved.

## Foreign table keys (FTK)

A column whose name ends in `ftk` (any casing), e.g. `tagFTK` or `tag_ftk`, is treated as a foreign key to the key column with the same base name in another table of the same database, even when SQL Server has no foreign key for it. The key column's name ends in:

| Ending                     | Examples                       |
| -------------------------- | ------------------------------ |
| `PK` (any casing)          | `tagPK`, `tag_PK`, `TagPk`     |
| a small letter + `TK`      | `tagTK` (but not `TAGTK`)      |
| `_tk` (any casing)         | `tag_tk`, `tag_TK`             |

So `Shirt.tagFTK` links to `Security.tagPK`, `Security.tagTK` or `Security.tag_tk`. These columns are coloured like foreign keys, and when generating you are asked whether to include the referenced table too.
